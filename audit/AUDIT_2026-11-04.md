## Section 1 — `src/pipeline/classifier.py` (`train_and_evaluate`)

Flux réel, dans l'ordre : `_clean_and_filter_data` → `_prepare_features_and_labels`
(sélection de colonnes, `spectro_only`) → **filtre MI sur tout X** → `LabelEncoder`

### K1 — Le filtre `mi_top_k` est ajusté avant le split · **CONFIRMÉ, LATENT** (v6 : indéterminé)

- **Titre d'issue** : `fix: déplacer le filtre mutual_info (mi_top_k) dans le pipeline, après le split`
- **Labels** : bug, science · **Priorité** : P0 · **Effort** : S
- **Problème + preuve** — `src/pipeline/classifier.py:1599-1618` calcule la MI sur `X_all`/`y_all`
  (train + test), puis le split n'arrive qu'à `:1638` :
  ```python
  if mi_top_k is not None and mi_top_k > 0:
      try:
          mi_scores = mutual_info_classif(
              X_all.fillna(0), y_all, discrete_features=False
          )
  ```
  Aggravants : `fillna(0)` au lieu de l'imputer médian du pipeline ; pas de `random_state`
  (mesuré : le top-10 reste stable d'un appel à l'autre sur données continues, donc impact faible).
  Ampleur mesurée (pur bruit, n=200, p=300, top-10, 60 répétitions) : précision test
  **0,524 ± 0,007** si la MI voit tout, contre **0,487 ± 0,008** si elle ne voit que le train
  (attendu : 0,5). Le biais est réel mais faible, et il croît quand k/p et n diminuent.
- **Latent ou réalisé pour v6 ?** Le chemin n'est emprunté que si `mi_top_k > 0`
  (défaut `None`, `master.py:1161` ; widget `mi_topk` à 0 ⇒ `None`, `master.py:2655`).
  **Attention** : « 207 candidates » ne prouve **pas** que la MI n'a pas tourné.
  `feature_cols_before_fs` est copié **avant** le filtre MI (`classifier.py:1596`) et c'est
  cette liste que le rapport de session enregistre sous `feature_columns`
  (`master.py:3870`). La seule preuve possible est le `*_meta.json` de v6 :
  `len(feature_names_used) == 207` ⇒ MI non appliquée ; `< 207` ⇒ fuite réalisée.
- **Pourquoi c'est important** : la sélection voit les labels du test, donc les
  métriques sont biaisées vers le haut (faiblement avec 350 k lignes et top-k large,
  fortement si k est petit ou s'il y a beaucoup de features bruitées).
- **Correctif proposé** : transformeur `SelectKBest(partial(mutual_info_classif, random_state=rs), k=mi_top_k)`
  placé après `prep` dans `steps` (donc refait dans chaque pli de CV), et suppression du bloc
  `try/except: pass`. Enregistrer `mi_top_k` dans les métadonnées.
- **Vérification** : test T1 (plus bas) : permuter les labels des lignes de test ne doit pas
  changer les colonnes retenues. Le code actuel échoue (mesuré : 3/10 colonnes communes
  entre une sélection sur tout le jeu et une sélection sur le train seul).

### K2 — `StratifiedGroupKFold(n_splits=1)` lève toujours une erreur ; repli silencieux non stratifié · **CONFIRMÉ, LATENT**

- **Titre d'issue** : `fix: remplacer StratifiedGroupKFold(n_splits=1) par un split groupé stratifié réel`
- **Labels** : bug, science · **Priorité** : P1 · **Effort** : S
- **Problème + preuve** — `src/pipeline/classifier.py:1638-1653` :
  ```python
  cv_split = StratifiedGroupKFold(
      n_splits=1, shuffle=True, random_state=random_state
  )
  ...
  except Exception:
      gss = GroupShuffleSplit(
  ```
  sklearn refuse `n_splits < 2` (`ValueError`, levée dès le constructeur de `_BaseKFold`,
  voir la vérification synthétique en fin de section). Le `except Exception` sans log bascule donc **toujours** sur

### C1 — Par défaut, aucune garantie que les observations multiples d'un même objet restent du même côté du split · **LATENT (défaut actif)**, réalisé pour v6 : **Hypothèse probable**

- **Titre d'issue** : `fix: split groupé par source_id/designation par défaut`
- **Labels** : science, bug · **Priorité** : P0 · **Effort** : M
- **Problème + preuve** — sans `use_groups`, le split est un `StratifiedShuffleSplit` ligne à ligne
  (`classifier.py:1654-1659`). `use_groups=False` est le défaut partout (`master.py:1138`,
  `master.py:1850`). Aucun dédoublonnage par objet n'existe en amont : `objid` est
  l'index du catalogue (`gaia_crossmatcher.py:217-219`), donc une étoile observée sur deux plans a deux
  `obsid` et deux lignes. Utiliser `group_col="obsid"` ne protège rien (un `obsid` = une observation).
  Avec `group_col="source_id"`, les spectres sans match Gaia (ou nullifiés par le filtre
  RUWE, `gaia_crossmatcher.py:1046-1050`) ont `source_id = <NA>`. **Mesuré** : l'entraînement
  plante (`ValueError: Input groups contains NaN`, levée par `GroupShuffleSplit` hors du `try`).
  Le seul choix de groupe qui « marche », `obsid`, ne protège rien.
- **Pourquoi c'est important** : LAMOST DR5 contient beaucoup de ré-observations
  (même étoile, plans différents). Le modèle peut « reconnaître » l'étoile, ce qui gonfle les
  métriques du test. La quantité de doublons dans le jeu v6 n'est pas mesurable ici
  (pas de données) : **Hypothèse** à vérifier par `features_df.designation.duplicated().mean()`.
- **Correctif proposé** : construire une clé `star_id` = `source_id` si présent, sinon
  `designation` LAMOST (déjà exclue des features, `classifier.py:859`), sinon `obsid` ;
  activer le split groupé par défaut ; refuser les groupes NaN.
- **Vérification** : test T2 + assertion dans `train_and_evaluate` :
  `set(groups[tr]) ∩ set(groups[te]) == ∅`.

### C2 — Early stopping inopérant avec XGBoost ≥ 3, et validation incluse dans le fit · **RÉALISÉ** dans un venv neuf ; v6 : **Hypothèse probable**

- **Titre d'issue** : `fix: early stopping XGBoost 3.x (paramètre constructeur) sur une validation disjointe`
- **Labels** : bug, science · **Priorité** : P1 · **Effort** : S
- **Problème + preuve** — `classifier.py:1880-1903` :
  ```python
  X_tr_in, X_val_in, y_tr_in, y_val_in = train_test_split(X_train, y_train, ...)
  ...
  prep_for_es.fit(X_train, y_train)
  X_val_es = prep_for_es.transform(X_val_in)
  fit_params["clf__eval_set"] = [(X_val_es, y_val_in)]
  ```
  Deux défauts cumulés :
  1. **ES jamais armé** : `callbacks` / `early_stopping_rounds` ne sont ajoutés que s'ils figurent
     dans la signature de `XGBClassifier.fit` (`classifier.py:1904-1911`). Depuis XGBoost 3, ils n'y sont
     plus (mesuré sur 3.2.0 : `fit(X, y, sample_weight, base_margin, eval_set, verbose, xgb_model, …)`)
     et ils ne sont pas non plus posés sur le constructeur. **Mesuré** sur du bruit pur :
     300 arbres construits sur 300 ; la référence avec ES correct s'arrête à `best_iteration = 0`.
     v6 a été produit avec XGBoost 3.1.1 (README:256), une version postérieure à ce retrait,
     et l'ES est coché par défaut (`master.py:1135`, widget `master.py:2078`) : si v6 n'utilisait pas
     de recherche d'hyperparamètres, son « early stopping » n'a rien fait (**Hypothèse probable**,
     faute de config enregistrée, voir C7).
  2. `X_tr_in` n'est jamais utilisé : le fit final (`pipe.fit(X_train, …)`, `:1971`) contient
     les lignes de `X_val_in`. Même réparé, l'arrêt se ferait sur des données vues.
  Le test n'est pas contaminé : pas de fuite vers les métriques, mais la régularisation
  annoncée est fictive et le nombre d'arbres effectif ne correspond pas à ce qui est rapporté.
- **Correctif proposé** : `base_est.set_params(early_stopping_rounds=…)` ; fit sur `X_tr_in`
  avec `eval_set=[(X_val_in transformé)]` (poids découpés en conséquence) ; refit éventuel sur tout
  le train avec `n_estimators=best_iteration+1` ; enregistrer `best_iteration` dans les métadonnées.
- **Vérification** : test T4 : sur données de pur bruit (5 classes, 20 features N(0,1)),
  `best_iteration < 0.5·n_estimators`. Le code actuel construit `n_estimators` arbres.

### C5 — Seuils par classe appris sur des probabilités non calibrées, appliqués à des probabilités calibrées · **LATENT**

- **Titre d'issue** : `fix: ré-apprendre les seuils après calibration prefit`
- **Labels** : bug, science · **Priorité** : P1 · **Effort** : S
- **Problème + preuve** — en mode holdout, `ThresholdTunedClassifier.fit` apprend `thresholds_`

  (ou interdire la combinaison `tune_thresholds` + holdout).
- **Vérification** : test « seuils recalculés ⇒ `thresholds_` différents avant et après calibration

## Section 7a — `_log_and_report` : métriques publiées, importances, SHAP

Chaîne réelle : `X_te = X_all.iloc[te_idx]` (`master.py:3434-3437`) → `y_pred = clf.model_pipeline.predict(X_te)` (`:3441`) →
rapport de classification et matrice de confusion (`:3443-3464`) → balanced accuracy (`:3487`) → `proba = model_pipeline.predict_proba(X_te)`
(`:3505-3511`) → ROC/PR (`:3563-3671`) → calibration et Brier (`:3678-3727`) → importances (`:3730-3784`).

**Réponses aux 4 questions**
- **Ordre des colonnes de `predict_proba`** : aligné. Pour XGBoost, SoftVoting et MLP, les colonnes suivent `classes_ = 0..K−1` du `LabelEncoder`,
  dont `classes_` (tri lexicographique) est exactement `class_labels` (`classifier.py:1631-1636`). Les vraies classes sont encodées par
  `label_encoder.transform` (`master.py:3472-3474`) puis binarisées sur `np.arange(n_classes)` (`:3592`, `:3697`). Pour les autres modèles,
  `classes_` vaut `sorted(unique(y_train))`, ce qui est égal à `class_labels` tant que chaque classe est présente dans le train. C'est garanti
  par le `StratifiedShuffleSplit` et le seuil de 10 exemples par classe, mais **pas** par le repli `GroupShuffleSplit` (K2). Aucune assertion
  `classes_ == class_labels` dans le code : risque latent (R7-3).
- **Test seul, après calibration et seuils** : oui. `X_te` vient de `te_idx`. `model_pipeline` contient le calibrateur et le
  `ThresholdTunedClassifier`, donc `predict` applique les seuils et `predict_proba` renvoie les probabilités calibrées, sans seuils
  (ce qui est correct pour l'AUC, l'AP et le Brier). Le repli `X_te, y_te = X, y` (`:3438-3439`) n'est jamais emprunté, car `_split_info`
  est toujours défini.
- **Définitions** : la balanced accuracy est celle de sklearn (`sk_balanced_accuracy_score`, `:3487`). La « ROC-AUC macro » publiée
  (`session_report["roc_auc_macro"] = roc_auc_results["macro"]`, `:3909`) **n'est pas** `roc_auc_score(…, average="macro")` (R7-2).
- **Importances et SHAP** : importances par permutation calculées sur le **test**, mais étiquetées avec les mauvais noms (R7-1). SHAP est calculé
  sur des lignes du train et du test mélangées, après `prep` et `fs` (R7-4).

### R7-5 — `wl_det` : précision limitée au pixel, fenêtre de ±8 Å qui ne dit pas quelle raie a été trouvée · **RÉALISÉ**

- **Titre d'issue** : `fix: centroïde sub-pixel et identification de raie dans le référentiel au repos (vide)`
- **Labels** : science · **Priorité** : P2 · **Effort** : M
- **Preuve** — `wl_det = peak_wavelengths[best_local]` (`peak_detector.py:174-175`) est un nœud de la grille log-λ, sans interpolation.
  Pas de pixel mesuré : **1,51 Å à 6 563 Å**, soit ±0,75 Å de quantification. **Mesuré** sur les 30 FITS versionnés avec les paramètres du pipeline :
  écarts `λ_det − λ_ref` jusqu'à **−4,6 Å (Hα), −7,0 Å (Hβ), +6,1 Å (CaII K), −6,1 Å (CaII H), −7,3 Å (Mg b)**, pour un décalage attendu de
  +1,4 à +1,8 Å (air → vide, F2) ± quelques Å (Z). La règle « plus forte prominence dans ±8 Å » ne garantit pas d'avoir identifié la
  bonne raie : CaII H (3968) et Hε (3970,1) sont à 2 Å l'une de l'autre, les composantes du triplet Mg b s'étalent sur 17 Å, et du bruit
  peut l'emporter. La fenêtre d'EW (±20 Å) et la FWHM sont ensuite **centrées sur `wl_det`** (`feature_engineering.py:1271-1276`) : une
  mauvaise identification déplace l'intégration. Taux de détection mesurés : 28 à 30/30 par raie. Le pipeline « trouve » donc presque

- **Interaction F1/F2** : la prominence est mesurée en unités de médiane globale du flux (F1). Pour une même raie, elle dépend donc du
  niveau du continuum local (plus faible dans le bleu des étoiles froides). Le seuil 0,15 n'a pas le même sens d'un type spectral à l'autre.
  Corriger F2 (vide + Z) permettrait de réduire la fenêtre à environ ±3 Å.
- **Correctif proposé** : passer au référentiel au repos dans le vide (F2), centroïde parabolique sur 3 pixels, fenêtre ≈ 2 éléments de
  résolution, et prominence relative au continuum local.
- **Vérification** : raie gaussienne synthétique à 6564,61·(1+Z), avec Z tiré entre −1e-3 et 1e-3, et bruit S/N = 30 ⇒ `|λ_det/(1+Z) − 6564,61| < 0,3 Å`
  pour 95 % des tirages ; une raie parasite plus forte à 7 Å ne doit pas être choisie.

### R7-6 — Raie non détectée : `prominence = 0`, EW et FWHM NaN, puis EW = 0 après `stabilize_spectral_features` · **RÉALISÉ**

- **Titre d'issue** : `fix: distinguer « raie non détectée » de « raie d'intensité nulle »`
- **Labels** : science · **Priorité** : P2 · **Effort** : S
- **Preuve** — aucun pic : `analyze_spectrum` renvoie `{name: None}` (`peak_detector.py:213-215`), sans log. Dans `extract_features`,

- **Vérification** : spectre sans raie ⇒ `*_eq_width` ≈ 0 ± 3σ (mesuré, pas imputé) et `*_detected = 0` ; spectre avec Hβ masqué (NaN) ⇒ EW NaN.
